### 1.1 `D4-13` — 녹음 폐기 contracts (안 A 확정, **Stage 0 #16 변경**)

**결정: 안 A — `SESSION_TRANSITIONS` 에 전이 2행만 추가한다.**

| 항목 | 확정 내용 |
|---|---|
| 추가되는 전이 | `{ from: 'recording', to: 'abandoned', actor: 'caregiver', modes: ['recorded'] }` · `{ from: 'paused', to: 'abandoned', actor: 'caregiver', modes: ['recorded'] }` |
| 전이표 행 수 | **12 → 14** |
| `SessionStatus` | **8값 유지** (`discarded` 신규 값 **없음** — 안 B 미채택) |
| `AbandonedReason` enum | **만들지 않는다** (안 A′ 미채택 — plan-agent 는 A′ 를 권고했고 사용자가 **A** 를 택했다) |
| `CompletedReason` | 신규 값 **0건** |
| Error Code | 신규 **0건**. 허용되지 않은 전이는 기존 `SESSION_INVALID_TRANSITION` 이 처리한다 |
| `UploadStatus` | 신규 **0건** — `deleted` 가 이미 있다 |
| 업로드 중단 통지 | **`recordingApi.abort()` 를 추가하지 않는다.** 서버가 `abandoned` 전이를 받아 part 를 스스로 정리하는 것을 **Handoff 요구사항**으로 적는다 (`P4-BIP-21`) |

⚠️ **명시 기록 — 이 결정의 귀결**

1. **방치(ready 10분)와 사용자 폐기(`Discard`)를 구분할 수 없다.** 둘 다 `→ abandoned`, actor `caregiver` 이므로 전이표·`session_events` 만 보고는 구별되지 않는다.
2. 따라서 **세션 완료율 지표(PRD §2)에서 둘을 분리 집계할 수 없고**, *"아동 음성 데이터를 사용자가 직접 지운 사건"* 의 Audit 근거도 전이 기록만으로는 남지 않는다 (`rules/backend.md` §4 Audit Log).
3. **나중에 Audit·지표가 필요해지면 사유 값 추가가 별도 결정이 된다** — `AbandonedReason` 또는 동등한 수단의 도입은 **그 시점의 사용자 결정 사항**이며, Stage 4 에서 선행 구현하지 않는다 (`N4-30`, 비차단·이연).
4. 서버 구현 측에서 사유를 남기려면 **Frontend 가 보내지 않는 정보**(요청 출처·타이머 여부)를 서버가 추론해야 한다 → Handoff 에 *"Frontend 는 폐기 사유를 보내지 않는다"* 를 명시한다.

**문서 일치**: `docs/API_CONTRACTS.md` **§6 `G-09`**(`:952`)가 이미 같은 안을 적어 두었다 — *"완료 전 폐기 = `abandoned` + 로컬 삭제, 서버 업로드 없음"*. 따라서 `G-09` 는 **Resolved (안 A)** 로 갱신한다.

**삭제 순서 (불변)**: **서버 전이 확정 응답을 받은 뒤 로컬을 지운다.** 전이 실패 시 로컬 청크를 **보존**하고, 오프라인이면 `SessionOutbox` 에 폐기 전이를 적재한 뒤 전송 확정 전까지 보존한다. `rules/architecture.md` §7 의 *"업로드 확정 전 삭제 금지"* 는 **유실 방지** 규칙이므로 사용자 주도 폐기는 그 규칙이 막으려는 사건이 아니다 — **예외가 아니라 다른 사건**으로 다룬다.
